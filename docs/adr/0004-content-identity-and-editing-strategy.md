# ADR-0004: Content Identity, Immutability & Editing Strategy

* **Status:** Proposed for Review
* **Date:** 2026-07-27
* **Authors:** Engineering & Product Team
* **Decider(s):** Product, Security & Editorial Lead

---

## Context & Problem Statement

Senior contributors submit photos, videos, written memories, and short class messages without creating user accounts. Each submission includes a required display name (e.g. *"Jordan M."*).
We must define content ownership, editing permissions for authors and admins, timestamp tracking, immutability rules, and audit requirements to maintain archival authenticity and prevent session spoofing.

---

## Decision Drivers

1. **Archival Authenticity:** Memories and messages should reflect authentic, un-sanitized class moments at the time of submission.
2. **Accountless Security:** Without permanent user accounts, allowing post-submission edits by anonymous clients creates security risks (session key reuse, impersonation, content tampering).
3. **Editorial Stewardship:** Admins need robust moderation controls (hide/restore/delete) without rewriting students' personal words.
4. **Temporal Clarity:** Distinguishing when an item was uploaded (`submitted_at`) from when the senior-year moment occurred (`moment_at`).

---

## Considered Options

### Option 1: Full Client Post-Submission Editing (Author Editable)
Allow seniors to edit or delete their posts within their active session cookie duration.

- **Pros:** Seniors can fix typos or change captions shortly after posting.
- **Cons:** High security vulnerability. Because senior sessions are anonymous and ephemeral, session expiry or browser storage clearing locks authors out of editing. Conversely, shared devices could allow another student to edit someone else's post.

### Option 2: Post-Submission Immutability + Admin Moderation (Recommended)
Submitted content is **strictly immutable** for contributors post-submission. Admins can moderate visibility (`visible`, `hidden`, `deleted`) and collection tags, but **cannot edit** the author's display name or submitted body text.

- **Pros:** Guarantees archival authenticity; eliminates anonymous editing spoofing attacks; clear product expectation (*"Check your submission carefully before sharing"*); preserves original voice.
- **Cons:** Typos cannot be self-corrected by contributors (must ask Admin to hide item and re-submit).

### Option 3: Full Admin Content Editing
Allow Senior Admin to edit display names, captions, and body text of any contribution.

- **Pros:** Admin can fix typos or redact mild inappropriate words without deleting the item.
- **Cons:** Risks administrative tampering or altering the authentic voice of classmates. Compromises trust in the archive.

---

## Decision Outcome

**Chosen Option:** **Option 2 (Post-Submission Immutability + Admin Moderation)**.

### Policy Specifications:

1. **Content Ownership & Identity:**
   - Content is owned by the class capsule.
   - Author attribution is recorded via `ParticipantHandle` (display name entered at submission, normalized and raw) bound to the submission's anonymous `session_id`.

2. **Contributor Permissions & Immutability:**
   - Once submitted and confirmed, content items are **immutable**. Contributors cannot edit text, captions, or media, nor delete submissions directly.
   - The UI MUST explicitly inform contributors: *"Submissions are shared directly with your class and cannot be edited after posting."*

3. **Admin Moderation & Editing Capabilities:**
   - Admins **CAN**: Change visibility status (`visible` $\leftrightarrow$ `hidden` $\rightarrow$ `deleted`), manage collection tags, and trigger permanent deletion.
   - Admins **CANNOT**: Edit the submitted text body, caption, or author display name.

4. **Timestamp Policy:**
   - `submitted_at`: Immutable UTC timestamp generated by the server upon receipt.
   - `moment_at`: Optional user-specified date representing when the memory occurred (used for chronological timeline ordering).
   - `hidden_at` / `deleted_at`: System UTC timestamps recorded upon moderation actions.

5. **Audit History:**
   - All moderation lifecycle actions (hide, restore, delete, tag modification) append an entry to `audit_events`.

---

## Compliance & Verification

- Enforced in domain entities (`packages/domain`) by emitting immutability errors if a update request attempts to modify `body` or `authorHandleId`.
- Verified in API contracts by excluding PUT/PATCH content body endpoints for senior sessions.
